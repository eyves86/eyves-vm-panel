# 10 万级规模架构设计与分片方案

本文给出把 EyvesCloud 从「单机单库」演进到「10 万用户 + 数万被控节点」的目标架构、
关键设计决策、容量估算与阶段化迁移路线。每条设计都对应现状（见
`docs/developer/architecture.md`）里一个具体的瓶颈，不是通用套话。

## 1. 目标与非目标

**目标**
- 被控节点（agent）数量：数万级（本方案按 30,000 节点设计）。
- 用户（含子用户）数量：10 万级。
- 单容器操作与列表/搜索在规模下保持可用的尾延迟（P99 < 1s，列表分页 < 500ms）。
- 任一 cell 故障不影响其他 cell 的读写。

**非目标（本期不做）**
- 跨云多活的一致性强保证；先做「可恢复的最终一致」。
- 把 LXC/KVM 控制面下沉为独立微服务——数据面仍是被控节点本地进程。

## 2. 现状瓶颈（代码事实）

| # | 位置 | 瓶颈 | 规模后果 |
|---|------|------|----------|
| B1 | `internal/config/store_sqlite.go` `saveConfigToDB()` | 每次保存**在一个事务里 DELETE 全部表再 INSERT 整个内存快照**，且持全局 `AppConfigMu` 写锁 | 30 万容器时单次保存重写 30 万行；写操作串行化 |
| B2 | `nodes` 以 JSON 存于 `app_meta`（单行） | 任何节点变更重写整个节点列表 | 节点数越大，心跳/变更越慢 |
| B3 | `handleNodeHeartbeat` 每 10s/节点 | 3 万节点 = 3000 次心跳/秒，每次触发配置库写入 | 心跳吃掉全部写带宽 |
| B4 | 单进程单 SQLite | 只能纵向扩容 | 无法横向扩展 API 能力 |
| B5 | 主控同步代理 `/api/nodes/{id}/containers` → `/api/agent/*` | 主控承担全部节点流量与容器操作转发 | 主控成为扇出瓶颈与单点 |
| B6 | 遥测（CPU/内存/磁盘/流量）与配置同库 | 高频观测数据与低频配置数据混写 | 观测数据淹没有效写 |

P0（已上线）：写放大治理 Phase 1/2/3 已把 B1 在当前单机规模下的「无效全量重写」压到
最低（空闲落库 14→1/min、管理写 2→1 次），但**没有改变 B1 的 O(全量) 本质**，只是
消除了重复触发。真正进入 10 万级需要下面的结构性改造。

## 3. 目标架构总览

```text
                        ┌────────────────────────── 全局控制面 ──────────────────────────┐
   浏览器/API 客户端 ──►│  无状态 API 层（N 副本，LB）                                     │
                        │   - JWT 会话（无状态）+ Redis（吊销表 / 限流 / 幂等键）           │
                        │   - 全局用户目录（分片 Postgres：by tenant_id）                   │
                        └───────────────┬──────────────────────────────────────────────────┘
                                        │ 按 node → cell 路由
                        ┌───────────────▼───────────────┐
                        │  Cell Router（cell 元数据）    │
                        └───────────────┬───────────────┘
              ┌─────────────────────────┼─────────────────────────┐
        ┌─────▼─────┐             ┌─────▼─────┐             ┌─────▼─────┐
        │  Cell 0   │             │  Cell 1   │   ...       │  Cell N   │
        │ Agent GW  │             │ Agent GW  │             │ Agent GW  │   ← 无状态网关池
        │ 心跳入站   │             │           │             │           │
        │ Shard DB  │             │ Shard DB  │             │ Shard DB  │   ← 节点/容器元数据（按 cell 分库）
        └─────┬─────┘             └─────┬─────┘             └─────┬─────┘
              │  gRPC/HTTP 流                │                     │
        ┌─────▼─────┐                  ┌─────▼─────┐        ┌─────▼─────┐
        │ 被控节点  │  ...             │ 被控节点  │        │ 被控节点  │
        └───────────┘                  └───────────┘        └───────────┘

   遥测链路（与配置/元数据分离）：
     节点 ──► 遥测入站 ──► 消息队列 ──► 聚合器 ──► 时序库（观测），不写配置库
```

三条主轴：**cell 分片**（节点）、**用户目录分片**（用户）、**配置/遥测分离**。

## 4. 关键设计

### 4.1 Cell 分片（解决 B2/B3/B5）

把被控节点划分为 cell，每 cell 目标 512–1024 个节点（可调）。

- 每个节点在创建时分配一个 `cell_id`（一致性哈希或按可用区），映射长期稳定，避免频繁迁移。
- 每个 cell 拥有独立的「Agent 网关」池与独立的元数据分库（Postgres schema 或独立实例）。
- 主控只持有 `node_id → cell_id` 的全局映射（很小的表），容器操作按映射路由到对应 cell 网关。
- cell 网关无状态，可水平扩容；故障时只影响该 cell。

收益：节点/容器的读写被切分到 N 个分库，写入 QPS 与数据量都随 cell 数线性扩展；
cell 内故障隔离。

代价：跨 cell 的「全局列表」（如管理员查看全部节点）需要 fan-out 聚合 + 缓存，需专门设计
（见 4.7）。

### 4.2 心跳聚合（解决 B3）

心跳是**观测数据**，不应每次落配置/元数据库。

- 节点 → Agent 网关：使用流式（gRPC streaming / WebSocket / HTTP 批量）上报，网关在内存按
  `node_id` 合并。
- 网关 → 队列（NATS/Kafka）→ 聚合器：按 `node_id` 以 10–30s 窗口**合并**后，对
  `nodes.last_seen / 版本 / 资源摘要` 做**单条行级 upsert**（不是整表重写）。
- 高频资源曲线（CPU/内存/流量）走时序库；`last_seen` 等最新值走元数据分库。
- 3 万节点 @10s = 3000 msg/s 入站，经 10s 合并后落到 DB 约 **3000/10 = 300 upsert/s**，且
  分布到各 cell 分库，单库仅数十 upsert/s——完全可承受。

### 4.3 元数据存储：从「全量重写」到「行级 upsert」（解决 B1/B6）

- 迁移 SQLite → Postgres（或兼容的分布式 SQL）。表结构规范化：`nodes`、`containers`、
  `sub_users`、`tenants`、`api_keys`、`sec_groups` 等成为独立表。
- 所有写路径改为**定向 upsert / delete**，彻底废弃「读全量内存快照 → 清表 → 重插」。
- `AppConfig` 的「内存态 + 全局锁」拆分为：**小配置**（语言/品牌/SMTP 等，可继续内存缓存 +
  定向写）与**大业务数据**（节点/容器/用户，直接走分库 DAO，不放进全局单例）。
- 配置热路径保留进程内缓存，但缓存的是**查询结果**而非「唯一真相」，真相在分库。

> 关键不变量：任何单次用户操作只应写 O(受影响行) 行，绝不 O(全量)。

### 4.4 用户目录分片（10 万用户）

- 全局用户目录按 `tenant_id`（或 `user_id` 哈希）分片到多个 Postgres 分片。
- 鉴权保持 **JWT 无状态**：网关/API 副本本地验签，无需查库；仅在需要「即时吊销」时查
  Redis 吊销表（token_version / 黑名单），带短 TTL 缓存。
- 登录、改密等低频写走分片主库；列表/搜索走只读副本。
- 子用户与租户配额计数用 Redis 计数器 + 定期回写，避免每请求写库。

### 4.5 无状态 API 横向扩展（解决 B4）

- API 层不持有会话状态：JWT + Redis（限流桶、吊销、幂等键），可任意加副本。
- 限流：从进程内桶改为 Redis（或网关侧），保证多副本共享阈值；桶键继续遵守「不含攻击者可控
  输入」的既有约束（见 `scripts/ci-check.sh` 契约 #3）。
- 后台任务（到期扫描、流量统计、快照清理）用**分布式租约**（Redis/etcd）选主，确保集群内
  只有一个副本执行，避免 N 副本重复扫全库。

### 4.6 容器操作代理与背压（解决 B5）

- 主控不再直接同步转发每个容器请求；改为**异步作业 + 幂等键**：
  客户端提交操作 → 生成 job（幂等键）→ 投递到对应 cell 网关 → 网关调用节点 agent →
  结果回写作业状态，客户端轮询/订阅。
- 每个节点有并发上限；队列深度作为背压信号，过载时快速失败并给出可读错误（沿用
  「不做假 UI、失败要有反馈」的产品约束）。
- 长时操作（创建/重装/迁移）本就应异步；短读（列表/详情）走元数据分库直读，不经节点。

### 4.7 全局视图与观测

- 「全部节点/容器」列表：优先从**聚合只读副本**或物化视图读；确需实时 fan-out 时对各 cell
  并发查询 + 结果缓存（秒级 TTL），并对结果集分页（服务端分页，禁止一次性拉全量）。
- 观测：每 cell 一套指标 + 全局汇总；控制高基数标签（node_id 不进主指标标签，用样例/日志）。
- SLO：API P99、心跳入站延迟、cell 内写放大（每用户操作写入行数）、队列深度。

## 5. 容量估算（设计输入）

| 指标 | 假设 | 结果 |
|------|------|------|
| 节点数 | 30,000 | — |
| 心跳频率 | 10s/节点 | 3,000 msg/s 入站 |
| 心跳合并窗口 | 10s | ~300 元数据 upsert/s（分摊到各 cell 分库） |
| 每节点容器 | ~10 | ~300,000 容器元数据行 |
| 用户数 | 100,000 | 分片用户目录 |
| 并发 API | 5%（5,000）@ 0.2 req/s | ~1,000 QPS（API 副本线性扩展） |
| cell 规模 | 1,024 节点 | 约 30 个 cell（含冗余） |

## 6. 迁移路线（每阶段可独立上线、可回滚）

| 阶段 | 内容 | 对应瓶颈 | 回滚 |
|------|------|----------|------|
| P0 | 写放大治理 Phase 1/2/3（**已完成**） | B1（缓解） | 回退二进制 |
| P1 | 元数据迁移 Postgres（先单实例）：行级 upsert，配置/遥测分表 | B1/B6 | 双写 + 切换读；保留 SQLite 快照 |
| P2 | 心跳批处理 + Agent 网关（与现主控并存，先接管心跳） | B3 | 网关旁路，回退直连心跳 |
| P3 | Cell 分片：节点分配 cell_id，元数据按 cell 分库 | B2/B5 | cell 映射回退为单库 |
| P4 | 用户目录分片 + API 多副本 + Redis 会话/限流/租约 | B4 | 降回单副本 + 进程内限流 |
| P5 | 多集群/多区域（cell 跨集群，全局目录只读复制） | — | 按集群回退 |

**迁移原则**
- 每个阶段都先「双写 + 影子读」验证一致性，再切主读。
- 数据迁移支持断点续传与校验（现有 `docs/design-migration-data-transfer.md` 的思路可复用）。
- 每阶段上线前，用 `scripts/fresh-install-e2e.sh` 及规模压测脚本做回归。
- 契约防退化沿用 `scripts/ci-check.sh`：新增的不变量（如「单次操作写入行数 ≤ 阈值」）应补为断言。

## 7. 风险与取舍

- **分布式事务**：跨 cell 操作（迁移）无法单库事务；用 2PC 或 sagas + 补偿，接受最终一致。
- **cell 再平衡**：节点迁移 cell 成本高，优先「只增不迁」——新节点按当前负载分配，旧节点仅在
  cell 严重倾斜时迁移。
- **全局视图成本**：fan-out 聚合是新的复杂度来源，能用「聚合副本/物化视图」就不要实时 fan-out。
- **一致性降级**：从「强一致单库」变为「分片最终一致」，产品语义（尤其计费/额度）需明确
  可容忍的延迟窗口。
- **运维成本**：Postgres 分片 + 队列 + Redis + 时序库，运维面显著扩大；P1 之前不应提前引入
  队列/时序库（按需、随规模逐步引入）。
